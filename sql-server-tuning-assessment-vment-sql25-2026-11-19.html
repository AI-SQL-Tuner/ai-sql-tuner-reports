SQL Server Tuning Assessment – VMEnt\SQL25 – 2026-11-19

Tuning goal: Improve server reliability, remove blocking and deadlocks, and speed up the busiest database work.

Server: VMEnt\SQL25 (connection: VMEnt,51433) · SQL Server 2025, build 17.0.1000.7 · Enterprise Developer Edition · Databases examined in depth: RetailOps, ForumDemo, SalesDemo and ShopDemo.

Executive summary

Overall health: Needs attention. The server had no observed memory pressure, but missing recovery checks, an active blocking chain and repeated deadlocks create substantial reliability risk.

  1. Clear the ShopDemo blocking chain and remove the deliberate pause inside its open transaction so customer and order work can proceed.
  2. Establish and test backups, then check every listed database for damage so a failure can be recovered safely.
  3. Correct the two SalesDemo payment procedures that access the same tables in conflicting order, reducing recurring transaction failures.
  4. Update the server to an approved current build after testing, reducing avoidable stability and security risk.
  5. Correct the busiest inefficient lookups and inaccurate ForumDemo calculations to improve speed and prevent wrong results.

Checks covered server resources and maintenance, active blocking, captured deadlocks, database indexes and selected procedure definitions.

Server health

Recovery readiness is the main server-wide concern. No completed damage check was recorded for the listed user databases. Ten listed databases, including system databases, have no recorded full backup; several databases configured for point-in-time recovery have no recorded log backup. Update the backup policy, verify restores, run the checks below and install a tested current build. Memory was checked over about an hour and showed no pressure. Network connections observed across the network were encrypted.

  • Put full and, where required, log backups on a tested schedule; include the system databases.
  • Run the database checks during a suitable maintenance window, investigate any errors, then schedule repeat checks.
  • Test and apply the approved server update.
  • Check disk capacity and use predictable transaction-log growth for the four identified databases.
Technical details
  • Installed build: 17.0.1000.7, SQL Server 2025 Enterprise Developer. The currency check identified build 17.0.5065.9 as CU11; confirm the currently approved build before patching.
  • No recorded full backup: master, model, msdb, BenchDeploy, IndexTunerChallenge, IndexTunerChallenge_bench_challenge, TunerBench, RubricArchive, SQLStormOltp_bench_sqlstorm-oltp and tpch10_bench_tpch10-realistic.
  • BenchDeploy, TunerBench and RubricArchive use FULL recovery without recorded log backups. Backup history does not establish whether external backup systems hold usable copies.
  • The server-health compilation counters are not used as a workload finding: the assessment’s own data collection was excluded.

Locking and blocking

A ShopDemo job deliberately paused while keeping a transaction open, and five other jobs were waiting. The longest observed wait was about five minutes. The paused job held up shipping; the waiting shipping work then held up customer and order reads. End the current chain through controlled job handling, then remove the pause from inside the transaction. Improving balance reads and making shipping failures release their transaction address secondary exposure, not the original pause.

  • Confirm the billing job’s rollback and retry behavior, then stop the current blocker through normal job control.
  • Change the job step so any required delay occurs only after its transaction has finished.
  • Deploy the shipping failure-handling change and the targeted balance search path after testing.
Technical details
  • The lead batch runs EXEC dbo.usp_ApplyLateFees, then WAITFOR DELAY '00:15:00' before rolling back its open transaction. The job-step definition was not available for a safe replacement script.
  • The downstream shipping statement updates dbo.Orders after updating dbo.Customers. The observed balance query scanned about 200,000 Orders rows.
  • The observed waits were lock waits, not evidence of memory pressure. A table-level lock was present, but a lock-escalation event was not established.

Deadlocks

The captured SalesDemo deadlocks share one avoidable conflict. Payment work holds an account change while seeking order data; refund work changes an order before seeking the account. Each can wait for the other, forcing one transaction to fail. Five complete cases show this pattern. Test and deploy the two procedure changes together, and confirm callers can safely handle a failed transaction. An additional quick-read setting might reduce one reader-versus-writer conflict, but it does not replace the code fix and is not included in this change set.

  • Test and deploy the paired payment and refund changes together, including checks for changed or missing orders and the required failure-handling behavior.
  • Make job retries depend on proof that repeating a payment or refund cannot duplicate its business effect.
Technical details
  • Resources in the complete graph are an Orders page and an Accounts key in SalesDemo. Payment requests a shared read on the order page; refund holds an intent lock there and requests the account key.
  • The paired scripts chosen below follow the complete deadlock graphs rather than the alternative procedure rewrites. Test carefully: these definitions read the order before opening a transaction and do not add transaction error handling; changed or missing rows and failure behavior need application-level review before release.
  • The observed cycle does not establish that the separate ShopDemo blocking chain is a deadlock.

RetailOps indexes

Existing search paths are the best starting point. An index already exists for the suggested customer region search, and an existing order-date index can serve the daily report after its date condition is corrected. Three small indexes were fragmented, but the available evidence does not establish enough user-facing benefit to put a rebuild ahead of the code and recovery changes. The large order-lines table is a possible candidate for a separate reporting structure, but that added write and storage cost needs a measured test before deployment.

Technical details
  • dbo.Customers already has IX_Customers_Region; the server-wide missing-index suggestion overlaps it.
  • The date rewrite can use dbo.Orders.IX_Orders_OrderDate. Its observed zero reads cover only the short post-restart interval and do not justify dropping it.
  • dbo.OrderLines has about 3 million rows. The proposed analytic index was estimated by the assessment at about 60–180 MB, based on four stored columns and unknown numeric widths; its net benefit was not measured.

RetailOps code

Several busy procedures do more work than necessary, and one cart procedure has a concurrency risk. The phone lookup scans an existing search path because its input type differs from the stored value. The email lookup changes the indexed value before comparing it, although the database comparison is already case-insensitive. Daily sales calculates a date for each order instead of searching a date range. Loyalty updates repeat customer-by-customer work. Test the matching procedure replacements together with their callers.

  • Match the phone input to its stored format and compare email directly.
  • Use a start and end date for daily sales, then check its actual runtime with the existing date index.
  • Calculate loyalty tiers as a group during a suitable quiet period.
  • Make simultaneous additions of the same cart item safe.
Technical details
  • Customers.Phone is varchar(20); usp_FindCustomerByPhone currently takes nvarchar(20). Check whether callers send characters the stored format cannot represent.
  • usp_GetCustomerOrderHistory applies UPPER to indexed Email; the database uses a case-insensitive collation.
  • usp_GetDailySales wraps Orders.OrderDate in DATEDIFF. Its rewrite uses the existing column directly.
  • The loyalty procedure repeatedly invokes fn_CustomerSpend; an inner statement ran about 300,000 times.

Replace these only after confirming the intended result contract. Removing a separate five-second pause will shorten the time updates hold locks; no observed blocking chain was attributed to this procedure.

SalesDemo indexes

One additional search path addresses repeated account-total calculations. The payment workload frequently sums order amounts by account and status, while the current order access scans more widely. Add the consolidated account-and-status index after testing the extra cost on this write-heavy table. The existing primary-key searches and page density need no change.

  • Build the single account-and-status index and assess payment and refund work after deployment.
Technical details
  • The chosen index is dbo.Orders(AccountId, Status) INCLUDE (Amount). It consolidates the overlapping server-wide, index and procedure suggestions into one change.
  • The alternative filtered index would largely duplicate this access path because the frequent calculation includes the common Open status. Its script is omitted.
  • The table has about 50,000 rows. The assessment’s narrower candidate estimate was about 1.5 MB; the included Amount makes final size greater, but its exact width-related storage effect was not established.

SalesDemo code

The payment procedure’s repeated total calculation is the main measured code cost. Its new index addresses that calculation; the coordinated procedure replacements address the separate deadlock cycle described above. These changes must be tested together. Both existing procedures have explicit transactions without complete failure handling, and the selected deadlock fixes do not resolve that omission.

Technical details
  • dbo.usp_PayOrder recorded about 14 million logical reads during its longer workload-history window.
  • Before production release, test the selected procedures for an absent order, changes between the initial read and the transaction, and errors after the transaction begins. No combined, tested rewrite addressing all three issues was provided.

ShopDemo code

Shipping needs safer failure handling, while two order searches can be narrowed. The shipping procedure can leave an open transaction if its later update fails; its replacement rolls back and passes the error on. An overdue-order search path can reduce late-fee scan work, while a separate customer-balance path reduces broad reads. Neither search path removes the deliberate pause in the billing job.

  • Deploy and test the shipping failure-handling change.
  • Add the balance and overdue-order search paths, allowing for extra work on order updates.
  • Use a single captured time for each newly placed order.
Technical details
  • usp_ApplyLateFees filters dbo.Orders by Status = 'Open' and overdue DueDate. The filtered index supports that predicate.
  • usp_CustomerBalance filters by CustomerId and Status and totals Total plus LateFee. One covering-index script was selected; the duplicate was omitted.

Limitations

  • Index-usage and recent runtime observations cover only about 32 hours after restart. They do not establish how infrequent or seasonal work behaves.
  • Seven lower-load user databases were not examined in depth. ShopDemo was added because blocking was active there.
  • Some summaries and script lists were shortened. One ForumDemo collection procedure was also incomplete; it is assessment machinery, not a basis for an application change.
  • Backup history does not prove whether external backups exist or can be restored. Their location, retention and recovery requirements must be confirmed.
  • The ShopDemo billing job definition was unavailable, so its unsafe pause cannot be replaced by a verified script here. The SalesDemo procedure scripts also need business-rule and failure-path testing before production use.

Align payment table access — Deadlocks — SalesDemo

USE [SalesDemo];
GO
CREATE OR ALTER PROCEDURE dbo.usp_PayOrder @OrderId int
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @AccountId int,
            @Amount decimal(12,2);

    SELECT
        @AccountId = AccountId,
        @Amount = Amount
    FROM dbo.Orders
    WHERE OrderId = @OrderId;

    BEGIN TRANSACTION;
        UPDATE dbo.Accounts
           SET Balance = Balance - @Amount,
               UpdatedAt = SYSDATETIME()
         WHERE AccountId = @AccountId;

        UPDATE dbo.Accounts
           SET OpenOrderTotal =
               (SELECT SUM(o.Amount)
                  FROM dbo.Orders AS o
                 WHERE o.AccountId = @AccountId
                   AND o.Status IN ('Open', 'Refunded'))
         WHERE AccountId = @AccountId;

        INSERT dbo.Payments (OrderId, Amount, Kind, CreatedAt)
        VALUES (@OrderId, @Amount, 'Payment', SYSDATETIME());

        UPDATE dbo.Orders
           SET Status = 'Paid',
               UpdatedAt = SYSDATETIME()
         WHERE OrderId = @OrderId;
    COMMIT;
END;
GO

Align refund table access — Deadlocks — SalesDemo

USE [SalesDemo];
GO
CREATE OR ALTER PROCEDURE dbo.usp_RefundOrder @OrderId int
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @AccountId int,
            @Amount decimal(12,2);

    SELECT
        @AccountId = AccountId,
        @Amount = Amount
    FROM dbo.Orders
    WHERE OrderId = @OrderId;

    BEGIN TRANSACTION;
        UPDATE dbo.Accounts
           SET Balance = Balance + @Amount,
               UpdatedAt = SYSDATETIME()
         WHERE AccountId = @AccountId;

        UPDATE dbo.Orders
           SET Status = 'Refunded',
               UpdatedAt = SYSDATETIME()
         WHERE OrderId = @OrderId;

        INSERT dbo.Payments (OrderId, Amount, Kind, CreatedAt)
        VALUES (@OrderId, -@Amount, 'Refund', SYSDATETIME());
    COMMIT;
END;
GO

Make shipping failures release the transaction — Code — ShopDemo

USE [ShopDemo];
GO

CREATE OR ALTER PROCEDURE dbo.usp_ShipOrder
    @OrderId int,
    @CustomerId int
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRY
        BEGIN TRANSACTION;

        UPDATE dbo.Customers
           SET LastOrderDate = SYSDATETIME()
         WHERE CustomerId = @CustomerId;

        UPDATE dbo.Orders
           SET Status = 'Shipped'
         WHERE OrderId = @OrderId;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF XACT_STATE() <> 0
            ROLLBACK TRANSACTION;

        THROW;
    END CATCH;
END;

Correct user and post counts — Code — ForumDemo

USE [ForumDemo];
GO

CREATE OR ALTER PROCEDURE dbo.sp00060
AS
BEGIN
    SET NOCOUNT ON;

    ;WITH PostCounts AS
    (
        SELECT
            p.OwnerUserId AS UserId,
            COUNT_BIG(*) AS TotalPosts
        FROM dbo.Posts AS p
        WHERE p.OwnerUserId IS NOT NULL
        GROUP BY p.OwnerUserId
    ),
    VoteCounts AS
    (
        SELECT
            p.OwnerUserId AS UserId,
            SUM(CASE WHEN v.VoteTypeId = 2 THEN 1 ELSE 0 END) AS UpVotes,
            SUM(CASE WHEN v.VoteTypeId = 3 THEN 1 ELSE 0 END) AS DownVotes
        FROM dbo.Posts AS p
        LEFT JOIN dbo.Votes AS v
            ON v.PostId = p.Id
           AND v.VoteTypeId IN (2, 3)
        WHERE p.OwnerUserId IS NOT NULL
        GROUP BY p.OwnerUserId
    ),
    BadgeCounts AS
    (
        SELECT
            b.UserId,
            COUNT_BIG(*) AS BadgeCount
        FROM dbo.Badges AS b
        GROUP BY b.UserId
    ),
    RankedPosts AS
    (
        SELECT
            p.OwnerUserId,
            p.Id AS PostId,
            p.Title,
            p.CreationDate,
            ROW_NUMBER() OVER
            (
                PARTITION BY t.Id
                ORDER BY p.CreationDate DESC, p.Id DESC
            ) AS rn,
            t.TagName
        FROM dbo.Posts AS p
        INNER JOIN dbo.Tags AS t
            ON p.Tags LIKE '%' + t.TagName + '%'
        WHERE p.PostTypeId = 1
    ),
    TopUsers AS
    (
        SELECT
            u.Id AS UserId,
            u.DisplayName,
            CONVERT(int, ISNULL(pc.TotalPosts, 0)) AS TotalPosts,
            CONVERT(int, ISNULL(vc.UpVotes, 0)) AS UpVotes,
            CONVERT(int, ISNULL(vc.DownVotes, 0)) AS DownVotes,
            CONVERT(int, ISNULL(bc.BadgeCount, 0)) AS BadgeCount,
            DENSE_RANK() OVER
            (
                ORDER BY
                    ISNULL(pc.TotalPosts, 0) DESC,
                    ISNULL(vc.UpVotes, 0) - ISNULL(vc.DownVotes, 0) DESC
            ) AS UserRank
        FROM dbo.Users AS u
        LEFT JOIN PostCounts AS pc
            ON pc.UserId = u.Id
        LEFT JOIN VoteCounts AS vc
            ON vc.UserId = u.Id
        LEFT JOIN BadgeCounts AS bc
            ON bc.UserId = u.Id
        WHERE ISNULL(pc.TotalPosts, 0) > 10
    )
    SELECT
        tu.UserRank,
        tu.DisplayName,
        tu.TotalPosts,
        tu.UpVotes,
        tu.DownVotes,
        tu.BadgeCount,
        rp.Title AS LatestPostTitle,
        rp.CreationDate AS LatestPostDate,
        CASE
            WHEN rp.rn = 1 THEN 'Latest'
            ELSE 'Older'
        END AS PostStatus
    FROM TopUsers AS tu
    LEFT JOIN RankedPosts AS rp
        ON rp.OwnerUserId = tu.UserId
    ORDER BY
        tu.UserRank,
        rp.CreationDate DESC;
END;
GO

Correct post counts and badge selection — Code — ForumDemo

USE [ForumDemo];

CREATE OR ALTER PROCEDURE dbo.sp09994
AS
BEGIN
    SET NOCOUNT ON;

    ;WITH CommentCounts AS
    (
        SELECT
            c.PostId,
            COUNT_BIG(*) AS CommentCount
        FROM dbo.Comments AS c
        GROUP BY c.PostId
    ),
    VoteCounts AS
    (
        SELECT
            v.PostId,
            SUM(CASE WHEN v.VoteTypeId = 2 THEN 1 ELSE 0 END) AS UpVotes,
            SUM(CASE WHEN v.VoteTypeId = 3 THEN 1 ELSE 0 END) AS DownVotes
        FROM dbo.Votes AS v
        WHERE v.VoteTypeId IN (2, 3)
        GROUP BY v.PostId
    ),
    RankedPosts AS
    (
        SELECT
            p.Id AS PostId,
            p.OwnerUserId,
            p.Title,
            p.Score,
            p.ViewCount,
            p.CreationDate,
            p.LastActivityDate,
            CONVERT(int, ISNULL(cc.CommentCount, 0)) AS CommentCount,
            CONVERT(int, ISNULL(vc.UpVotes, 0)) AS UpVotes,
            CONVERT(int, ISNULL(vc.DownVotes, 0)) AS DownVotes,
            ROW_NUMBER() OVER
            (
                ORDER BY
                    p.Score DESC,
                    p.ViewCount DESC,
                    p.CreationDate DESC,
                    p.Id DESC
            ) AS [Rank]
        FROM dbo.Posts AS p
        LEFT JOIN CommentCounts AS cc
            ON cc.PostId = p.Id
        LEFT JOIN VoteCounts AS vc
            ON vc.PostId = p.Id
        WHERE p.PostTypeId = 1
          AND p.CreationDate >= DATEADD(YEAR, -1, CAST('2024-10-01T12:34:56' AS datetime))
    ),
    TopPosts AS
    (
        SELECT
            rp.PostId,
            rp.OwnerUserId,
            rp.Title,
            rp.Score,
            rp.ViewCount,
            rp.CreationDate,
            rp.LastActivityDate,
            rp.CommentCount,
            rp.UpVotes,
            rp.DownVotes,
            rp.[Rank]
        FROM RankedPosts AS rp
        WHERE rp.[Rank] <= 10
    )
    SELECT
        tp.PostId,
        tp.Title,
        tp.Score,
        tp.ViewCount,
        tp.CreationDate,
        tp.LastActivityDate,
        tp.CommentCount,
        tp.UpVotes,
        tp.DownVotes,
        COALESCE(b.Name, 'No Badge') AS TopBadge
    FROM TopPosts AS tp
    OUTER APPLY
    (
        SELECT TOP (1)
            b.Name
        FROM dbo.Badges AS b
        WHERE tp.UpVotes > 100
          AND b.UserId = tp.OwnerUserId
        ORDER BY
            b.Class ASC,
            b.Date DESC,
            b.Id DESC
    ) AS b
    ORDER BY
        tp.Score DESC,
        tp.ViewCount DESC;
END;

Remove the pause between table updates — Code — ForumDemo

USE [ForumDemo];
GO

CREATE OR ALTER PROCEDURE dbo.usp_UpdateTablesWithDelay
    @UserId INT,
    @NewReputation INT,
    @PostId INT,
    @NewScore INT
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRY
        BEGIN TRANSACTION;

        UPDATE dbo.Users
        SET Reputation = @NewReputation,
            LastAccessDate = GETDATE()
        WHERE Id = @UserId;

        DECLARE @RowsAffected1 INT = @@ROWCOUNT;

        UPDATE dbo.Posts
        SET Score = @NewScore,
            LastActivityDate = GETDATE()
        WHERE Id = @PostId;

        DECLARE @RowsAffected2 INT = @@ROWCOUNT;

        COMMIT TRANSACTION;

        SELECT
            'Success' AS Status,
            'Both tables updated successfully' AS Message,
            @RowsAffected1 AS UsersRowsAffected,
            @RowsAffected2 AS PostsRowsAffected;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0
            ROLLBACK TRANSACTION;

        SELECT
            'Error' AS Status,
            ERROR_NUMBER() AS ErrorNumber,
            ERROR_MESSAGE() AS ErrorMessage,
            ERROR_LINE() AS ErrorLine,
            ERROR_PROCEDURE() AS ErrorProcedure;

        THROW;
    END CATCH;
END;
GO

CREATE OR ALTER PROCEDURE dbo.usp_GetDailySales
    @ReportDate date
AS
BEGIN
    SET NOCOUNT ON;

    SELECT p.Category,
           COUNT(DISTINCT o.OrderId) AS Orders,
           SUM(ol.Quantity * ol.UnitPrice) AS Revenue
    FROM dbo.Orders AS o
    JOIN dbo.OrderLines AS ol
        ON ol.OrderId = o.OrderId
    JOIN dbo.Products AS p
        ON p.ProductId = ol.ProductId
    WHERE o.OrderDate >= @ReportDate
      AND o.OrderDate < DATEADD(day, 1, @ReportDate)
      AND o.Status <> 'Cancelled'
    GROUP BY p.Category
    ORDER BY Revenue DESC;
END;
GO

Calculate loyalty tiers together — Code — RetailOps

CREATE OR ALTER PROCEDURE dbo.usp_RecalcLoyaltyTiers
    @Region varchar(20),
    @AsOf date
AS
BEGIN
    SET NOCOUNT ON;

    ;WITH RegionalSpend AS
    (
        SELECT o.CustomerId,
               SUM(ol.Quantity * ol.UnitPrice) AS Spend
        FROM dbo.Customers AS c
        JOIN dbo.Orders AS o
            ON o.CustomerId = c.CustomerId
        JOIN dbo.OrderLines AS ol
            ON ol.OrderId = o.OrderId
        WHERE c.Region = @Region
          AND o.OrderDate >= DATEADD(year, -1, @AsOf)
          AND o.OrderDate < @AsOf
          AND o.Status <> 'Cancelled'
        GROUP BY o.CustomerId
    )
    UPDATE c
       SET LoyaltyTier =
           CASE
               WHEN COALESCE(rs.Spend, CONVERT(decimal(14, 2), 0)) >= 12500 THEN 'Gold'
               WHEN COALESCE(rs.Spend, CONVERT(decimal(14, 2), 0)) >= 9500 THEN 'Silver'
               ELSE 'Bronze'
           END
    FROM dbo.Customers AS c
    LEFT JOIN RegionalSpend AS rs
        ON rs.CustomerId = c.CustomerId
    WHERE c.Region = @Region;
END;
GO

CREATE OR ALTER PROCEDURE dbo.usp_AddCartItem
    @CartId int,
    @ProductId int,
    @Quantity int
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRY
        BEGIN TRANSACTION;

        UPDATE ci WITH (UPDLOCK, SERIALIZABLE)
           SET Quantity = Quantity + @Quantity
        FROM dbo.CartItems AS ci
        WHERE ci.CartId = @CartId
          AND ci.ProductId = @ProductId;

        IF @@ROWCOUNT = 0
        BEGIN
            INSERT dbo.CartItems
                (CartId, ProductId, Quantity)
            VALUES
                (@CartId, @ProductId, @Quantity);
        END;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF XACT_STATE() <> 0
            ROLLBACK TRANSACTION;

        THROW;
    END CATCH;
END;
GO
