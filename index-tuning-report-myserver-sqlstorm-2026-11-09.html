Detailed prioritized recommendations

Priority 1 — Add consolidated indexes for dbo.PostHistory

The missing-index signals overlap around PostId, CreationDate, PostHistoryTypeId, UserId, and Comment. The recommended consolidation is:

  • PostId, CreationDate, PostHistoryTypeId INCLUDE Comment — estimated 45.3 MB for 847,593 rows, using the supplied candidate estimate.
  • CreationDate, UserId INCLUDE Comment — estimated 32.3 MB for 847,593 rows, using the supplied candidate estimate.
  • PostHistoryTypeId, PostId, CreationDate INCLUDE Comment — estimated 32.3 MB for 847,593 rows, using the supplied candidate estimate. This also addresses the type-led candidate signals while retaining join columns.

The Comment column is varchar(800) with a sampled average width of 32 bytes, so it is narrow enough for these candidates according to the input. The input does not identify Comment as a MAX or LOB column. The reported 99.62% impact and 48 total seeks/scans support the first family most strongly. The remaining families have lower reported seek/scan counts, so confidence is medium.

Priority 2 — Add the dbo.Votes user-oriented covering index

Create (UserId) INCLUDE (VoteTypeId, BountyAmount). The missing-index recommendation reports average impact of 99.51%, average total user cost of 4,137.06, and 15 total seeks/scans. The supplied candidate size is 28.3 MB for 926,084 rows. This complements, rather than duplicates, the existing IX_Votes_PostId_VoteType, which is keyed by PostId and has 482 seeks and 457 scans during the 3.9-day window.

Priority 3 — Add the dbo.Comments(PostId) join index

Create (PostId). The recommendation reports 246 total seeks/scans and average impact of 37.50%. The supplied candidate estimate is 5.4 MB, but the input does not provide the final row count and width calculation for the exact index. The size should therefore be treated as a candidate estimate, not a measured post-build size.

Priority 4 — Re-trust the foreign keys conditionally

Every foreign key listed in the untrusted-constraint section is enabled but not trusted. An untrusted foreign key can prevent optimizer join elimination and reduce predicate-pruning opportunities. The script validates each relationship inline; it executes WITH CHECK CHECK CONSTRAINT only when no violating row exists and prints the constraint name when violations remain.

Priority 5 — Enable statistics creation and maintenance

AUTO_CREATE_STATISTICS, AUTO_UPDATE_STATISTICS, and asynchronous statistics updates are all reported as false. Enable them as separate changes. The supplied database is SQLStorm, and each setting script is independent so a rejected or deferred setting does not prevent the others from running.

Query workload findings

Tag substring search is non-seekable

The highest CPU plan-cache query, hash 872C7773968C6AAF, executed 4 times with average CPU time reported as 323,745,169 and average logical reads of 862,018. Its CTE contains p.Tags LIKE '%' + t.TagName + '%'. The leading wildcard prevents a normal B-tree seek on Tags. The same pattern appears in Query Store workload text with an average duration of 99,671.55 ms for 10 executions and 226,609 average reads in one related entry.

  • Prefer a normalized post-to-tag relationship table keyed by TagName and PostId, or a full-text/search solution appropriate to the required matching semantics.
  • Do not add an index merely on Posts.Tags for this predicate; it will not make the leading-wildcard expression seekable.
  • The existing IX_Posts_Question_TagScan may help filter question posts, but its 10.5 MB size, page compression, and 95 seeks do not solve the substring join.

Repeated fan-out aggregation should be decomposed

Many Query Store statements join Posts, Votes, Comments, and Badges before aggregating. This can multiply rows before COUNT(DISTINCT) and produce very high reads, writes, memory grants, and spills. Query hash 0D1DCC1B897CEF72 reports 42,503 spills and 594,368 KB maximum grant in plan cache. Query Store also reports examples with average durations from 147,742.26 ms to 303,112.89 ms.

  • Aggregate Votes, Comments, Badges, and PostHistory independently by their foreign-key column, then join the smaller aggregate results.
  • Keep the predicates on the bare columns. The supplied non-sargable-predicate analysis found no wrapped column predicates in the top 50 plan-cache statements, so no range rewrite is required for the reported date predicates.
  • Use Query Store to compare the rewritten statement against the original. No estimated execution plans were supplied, so a before/after operator-cost comparison cannot be stated.

Examples of statements benefiting from the recommended indexes

  • Query Store statements containing LEFT JOIN Comments c ON p.Id = c.PostId benefit from Comments(PostId).
  • Statements aggregating votes by user or joining v.UserId = u.Id benefit from Votes(UserId) INCLUDE (VoteTypeId, BountyAmount).
  • Statements containing ph.PostId, ph.PostHistoryTypeId, and date or close-history predicates benefit from the consolidated PostHistory indexes.
