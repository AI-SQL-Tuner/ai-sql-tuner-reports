Detailed prioritized recommendations

  1. Priority 1 — Replace the multi-way user aggregate with independent aggregates

    Finding. The original query joins every user’s Posts to Votes and Badges before grouping. That multiplies each post-vote row by the user’s badge count. It then uses COUNT(DISTINCT ...) twice to recover distinct post and badge counts. The plan estimates 1,677,120 rows before the aggregate and 167,486 rows at the aggregate output.

    Recommendation. Aggregate posts, votes, and badges separately, then join the small per-user result sets. The rewrite below intentionally calculates vote totals as the original does: vote counts are multiplied by badge count when at least one badge exists, and are multiplied by one when the left join supplies the single null badge row. This preserves the original rows and values, including its unusual semantics.

    Evidence: Hash Match Aggregate node 18 estimates 167486 rows and consumes node 19’s 1677120 rows. The aggregate has two distinct aggregates, for Posts.Id and Badges.Id.

    Expected benefit. High potential, but not numerically guaranteed from the supplied data. It targets the aggregate branch’s 1.677 million-row intermediate result and removes redundant distinct processing. The plan assigns only 4.8827 subtree cost to the current user-statistics branch, so the overall gain may be materially smaller than the tag-join gain.

  2. Priority 2 — Eliminate or redesign the leading-wildcard tag relationship

    Finding. The predicate p.Tags LIKE '%' + t.TagName + '%' is non-sargable. The plan uses Nested Loops with a Lazy Spool and estimates 104,582 output rows. The Nested Loops operator’s own cost is 157.5283, representing 79% of the total estimated cost.

    Recommendation. The durable design is a normalized bridge table containing one row per PostId/TagId, populated from the tag representation at write or ETL time. A full-text index is not a safe equivalent because tokenization and word-boundary behavior do not necessarily match substring semantics. No bridge-table script is provided because no such table appears in the supplied metadata, and creating one would change the schema and require a validated parser and data-load process.

    Evidence: Clustered Index Scan node 9 reads 246,672 Posts rows; Tags node 12 reads 1,232 rows; the join predicate is shown as Posts.Tags LIKE Expr1020.

    Short-term option. Retain the current scan but reduce the number of columns flowing through it only after measuring. A conventional index on Tags or Posts.Tags will not make the leading wildcard seekable and should not be added solely because of this plan.

Rewritten query — Recommendation 1

USE [SQLStormOltp];
GO

;WITH RankedPosts AS
(
    SELECT
        p.Id AS PostId,
        p.Title,
        p.CreationDate,
        ROW_NUMBER() OVER
        (
            PARTITION BY t.Id
            ORDER BY p.CreationDate DESC
        ) AS rn,
        t.TagName
    FROM dbo.Posts AS p
    JOIN dbo.Tags AS t
        ON p.Tags LIKE '%' + t.TagName + '%'
    WHERE p.PostTypeId = 1
),
PostCounts AS
(
    SELECT
        p.OwnerUserId AS UserId,
        COUNT_BIG(*) AS TotalPosts
    FROM dbo.Posts AS p
    GROUP BY p.OwnerUserId
),
VoteCounts AS
(
    SELECT
        p.OwnerUserId AS UserId,
        SUM(CASE WHEN v.VoteTypeId = 2 THEN 1 ELSE 0 END) AS UpVotes,
        SUM(CASE WHEN v.VoteTypeId = 3 THEN 1 ELSE 0 END) AS DownVotes
    FROM dbo.Posts AS p
    LEFT JOIN dbo.Votes AS v
        ON p.Id = v.PostId
    GROUP BY p.OwnerUserId
),
BadgeCounts AS
(
    SELECT
        b.UserId,
        COUNT_BIG(*) AS BadgeCount
    FROM dbo.Badges AS b
    GROUP BY b.UserId
),
UserStats AS
(
    SELECT
        u.Id AS UserId,
        u.DisplayName,
        CONVERT(int, ISNULL(pc.TotalPosts, 0)) AS TotalPosts,
        CONVERT
        (
            int,
            ISNULL(vc.UpVotes, 0)
            * CASE
                WHEN ISNULL(bc.BadgeCount, 0) = 0 THEN 1
                ELSE CONVERT(int, bc.BadgeCount)
              END
        ) AS UpVotes,
        CONVERT
        (
            int,
            ISNULL(vc.DownVotes, 0)
            * CASE
                WHEN ISNULL(bc.BadgeCount, 0) = 0 THEN 1
                ELSE CONVERT(int, bc.BadgeCount)
              END
        ) AS DownVotes,
        CONVERT(int, ISNULL(bc.BadgeCount, 0)) AS BadgeCount
    FROM dbo.Users AS u
    LEFT JOIN PostCounts AS pc
        ON u.Id = pc.UserId
    LEFT JOIN VoteCounts AS vc
        ON u.Id = vc.UserId
    LEFT JOIN BadgeCounts AS bc
        ON u.Id = bc.UserId
),
TopUsers AS
(
    SELECT
        us.UserId,
        us.DisplayName,
        us.TotalPosts,
        us.UpVotes,
        us.DownVotes,
        us.BadgeCount,
        DENSE_RANK() OVER
        (
            ORDER BY
                us.TotalPosts DESC,
                us.UpVotes - us.DownVotes DESC
        ) AS UserRank
    FROM UserStats AS us
    WHERE us.TotalPosts > 10
)
SELECT
    tp.UserRank,
    tp.DisplayName,
    tp.TotalPosts,
    tp.UpVotes,
    tp.DownVotes,
    tp.BadgeCount,
    rp.Title AS LatestPostTitle,
    rp.CreationDate AS LatestPostDate,
    CASE
        WHEN rp.rn = 1 THEN 'Latest'
        ELSE 'Older'
    END AS PostStatus
FROM TopUsers AS tp
LEFT JOIN RankedPosts AS rp
    ON tp.UserId = rp.PostId
ORDER BY
    tp.UserRank,
    rp.CreationDate DESC;
GO

The final join remains tp.UserId = rp.PostId deliberately, preserving the supplied query’s exact row relationship. The independent aggregates preserve the original vote multiplication caused by the Posts-to-Votes-to-Badges join.
