Detailed prioritized recommendations

1. Add a consolidated PostHistory access path

Recommendation: create a page-compressed nonclustered index on dbo.PostHistory(PostId, CreationDate, PostHistoryTypeId) including Comment.

This consolidates the reported PostId, PostId + CreationDate, and PostId + CreationDate + PostHistoryTypeId candidates. It also supports queries joining post history to posts and filtering history type 10 or 11. The supplied average Comment width is only 32 bytes despite the declared varchar(800); the estimate is 45.3 MB. The column is not a large object, so including it is reasonable for the reported candidate.

Evidence: the PostId suggestion reports 99.61% average impact and 55 total seeks/scans; the more selective composite suggestion reports 84.31% average impact. The existing clustered primary key is on Id and does not provide this access path.

Confidence: High for the access path; medium for exact runtime benefit because the usage window is only 3.9 days.

2. Add a date and user access path for PostHistory

Recommendation: create dbo.PostHistory(CreationDate, UserId) including Comment, page compressed. Estimated size: 32.3 MB for 847,593 rows, using the reported overlap candidate.

This serves the missing-index recommendation with 15 total seeks/scans and 52.41% average impact. It is intentionally separate from the PostId-leading index because CreationDate is not a leading key in the first index and the workload includes date-oriented history reporting.

Confidence: Medium-high. The recommendation is supported by a direct missing-index signal, but its lower total seek/scan count warrants a lower priority than the PostId-leading index.

3. Add a user-centered covering index on Votes

Recommendation: create dbo.Votes(UserId) including VoteTypeId, BountyAmount, page compressed. Estimated size: 28.3 MB for 926,084 rows.

The reported recommendation has 99.51% average impact and 15 total seeks/scans. It directly supports the many user aggregation statements in plan cache and Query Store, including the statement identified by query hash FE52206CED094538, which averaged 10,843,182 CPU time units and 236,115 logical reads over two executions in the plan-cache period.

The existing IX_Votes_PostId_VoteType is useful for post-centered access and should remain. It does not cover the leading UserId access pattern.

Confidence: High for user aggregation workloads; medium for total production benefit because writes and usage are observed for only 3.9 days.

4. Add the missing Comments foreign-key access path

Recommendation: create dbo.Comments(PostId), page compressed. Estimated size: 5.4 MB for 351,440 rows.

The missing-index report records 291 total seeks/scans and 36.79% average impact. Query Store statements repeatedly join comments by PostId, including the workload with query text beginning WITH PostStats AS (... LEFT JOIN Comments c ON p.Id = c.PostId ...).

Confidence: High. The index is narrow, inexpensive relative to the 78.1 MB clustered table, and supports a high-frequency join column.

5. Consider a filtered Badges index for the rare Class = 1 workload

Recommendation: add a filtered index on dbo.Badges(UserId) including Id with the predicate Class = 1. The histogram reports Class 1 at 2.30% of 439,352 rows. This is the exception to avoiding an unfiltered low-cardinality leading key: the predicate is selective and literal in the observed Query Store workload.

The existing IX_Badges_UserId_Id is heavily used, with 216 seeks and 233 scans, and is only 4.6 MB. Therefore this filtered index is optional rather than mandatory. A filtered index is reliably matched when the query contains the literal predicate or is recompiled; parameterized predicates may not use it unless the optimizer can prove the parameter value satisfies the filter.

Estimated size: the input does not provide a filtered-candidate size. A firm MB estimate is therefore unavailable; it should be materially below the 4.6 MB unfiltered index because the filter retains approximately 2.30% of the reported histogram rows. This is a medium-confidence optimization and should be deferred until the rare-Class-1 queries are confirmed as important.

6. Re-trust foreign keys after conditional validation

All 17 reported foreign keys are enabled but not trusted. An untrusted constraint blocks optimizer join elimination and predicate pruning. The script in the Scripts section checks each relationship and re-trusts it only when no violating rows exist; otherwise it prints the skipped constraint name. The validation scans may be expensive on large tables.

Confidence: High for optimizer correctness and plan quality; the performance effect depends on the individual query plans.

  • No duplicate-index drops: no duplicate or left-prefix overlaps were detected, and all four checked nonclustered indexes have no listed dependencies. Nevertheless, the usage period is too short for low-use drops, and no low-use drop is justified.
  • No low-density rebuild: all supplied indexes have average page density of at least 93.65%, well above the approximately 75% review threshold. Rebuilds, fill-factor changes, and page-split remediation are not justified.

  • Foreign-key coverage: the relationships are present, but their untrusted state reduces optimizer usefulness. Re-trusting is preferred over adding redundant foreign-key indexes unless a specific workload demonstrates the need.
