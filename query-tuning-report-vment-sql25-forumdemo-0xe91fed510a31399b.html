Detailed prioritized recommendations

  1. Rewrite the correlated subqueries as set-based aggregates

    Build the 2020 answer set once, aggregate votes once, and aggregate 2020 comments once. This preserves the original semantics: votes are filtered only by VoteTypeId and answer PostId, while comments are filtered by their 2020 CreationDate and answer PostId.

    Evidence: the current plan repeats the Votes clustered scan 87 times and estimates 505,869 logical reads in the measured Query Store execution. The rewrite directly targets this repeated work.

    Expected benefit: high, but the exact improvement must be measured. It should reduce repeated scans and may change the plan to hash or merge aggregates over each base table once.

  2. Add the Votes join-supporting index

    Create a nonclustered index on dbo.Votes(PostId, VoteTypeId). It supports the join from answer IDs to votes and the VoteTypeId filter. The clustered key Id is implicitly present as the row locator for a nonclustered index, but it is not needed by the count.

    Evidence: the plan reports a missing-index candidate with equality columns PostId and VoteTypeId and 96.44% estimated statement-cost impact. The DMV reports average user impact 99.42 and 80 seeks/scans. Existing IX_Votes_VoteTypeId has zero seeks.

    Estimated size: approximately 15–30 MB after creation. Basis: 945,284 rows, approximately 4-byte PostId plus 2-byte VoteTypeId, the implicit 4-byte clustered key, row/page overhead, and PAGE compression. The input does not provide a missing-index storage estimate, so this is a range rather than a measured size.

    Risk: additional insert/update/delete maintenance. Votes has 6,400 updates on each listed index during the 2.4-day observation period; the new index adds one more write target and requires statistics and index maintenance. Validate before retaining it.

  3. Use half-open date ranges

    For a datetime year, use a predicate equivalent to CreationDate >= '20200101' AND CreationDate < '20210101'. This is a non-executable illustrative fragment outside the Scripts section.

    Evidence: Posts uses datepart(year, CreationDate); Comments has the explicit plan-affecting conversion on the table column. Both CreationDate columns are datetime, and the Comments date column is NOT NULL.

    Expected benefit: improved selectivity and seekability when a suitable leading index is available; it also removes the conversion warning. It does not by itself guarantee a seek on the current indexes.

  4. Evaluate a Posts covering access path after the rewrite

    If the rewritten query still scans Posts or performs repeated lookups, create (PostTypeId, CreationDate, OwnerUserId) including Id. This matches the fixed post type and date range and supplies the answer owner and answer ID.

    Evidence: the current plan scans 246,672 Posts rows and the existing owner-only index estimates 7.0746 rows per user followed by clustered lookups. The plan already uses a user-created statistic named ST_Posts_PostType_Creation_Owner, but that statistic is not an index.

    Estimated size: approximately 20–40 MB. Basis: 246,672 rows, key widths of approximately 2 bytes for smallint PostTypeId, 8 bytes for datetime CreationDate and 4 bytes for OwnerUserId, included 4-byte Id, clustering-key overhead, and PAGE compression. Exact column metadata and candidate size are not supplied, so this is a range.

    Risk: Posts has 19,200 clustered-index updates in the observed period; the new index will add write and maintenance work. Because the existing IX_Posts_OwnerUserId has 16,120 seeks and only 3.3 MB size, do not drop or replace it based on this query alone.

  5. Evaluate a Comments date-covering index after the rewrite

    If the post-rewrite plan still performs many lookups, create (PostId, CreationDate). This supports answer-to-comment joins and the 2020 date range without converting the Comments column.

    Evidence: the existing IX_Comments_PostId has 32,000 seeks but operator 44 still performs clustered lookups with the date conversion. Comments has 365,839 rows, 4,800 updates in the observed period, and the existing index is only 5.1 MB.

    Risk: additional maintenance for 4,800 observed Comments updates. Retain the existing PostId index unless broader usage confirms that the new composite index makes it redundant; this report does not contain enough workload evidence to recommend dropping it.

Rewritten query — set-based answer, vote and comment aggregates

USE [ForumDemo];
GO

WITH AnswerPosts AS
(
    SELECT
        a.Id,
        a.OwnerUserId
    FROM dbo.Posts AS a
    WHERE a.PostTypeId = 2
      AND a.CreationDate >= '20200101'
      AND a.CreationDate < '20210101'
),
AnswerCounts AS
(
    SELECT
        ap.OwnerUserId,
        COUNT(*) AS Answers2020
    FROM AnswerPosts AS ap
    GROUP BY ap.OwnerUserId
),
UpvoteCounts AS
(
    SELECT
        ap.OwnerUserId,
        COUNT(*) AS Upvotes2020
    FROM AnswerPosts AS ap
    INNER JOIN dbo.Votes AS v
        ON v.PostId = ap.Id
       AND v.VoteTypeId = 2
    GROUP BY ap.OwnerUserId
),
CommentCounts AS
(
    SELECT
        ap.OwnerUserId,
        COUNT(*) AS Comments2020
    FROM AnswerPosts AS ap
    INNER JOIN dbo.Comments AS c
        ON c.PostId = ap.Id
       AND c.CreationDate >= '20200101'
       AND c.CreationDate < '20210101'
    GROUP BY ap.OwnerUserId
)
SELECT TOP (25)
    u.Id,
    u.DisplayName,
    u.Reputation,
    ac.Answers2020,
    ISNULL(uc.Upvotes2020, 0) AS Upvotes2020,
    ISNULL(cc.Comments2020, 0) AS Comments2020
FROM dbo.Users AS u
INNER JOIN AnswerCounts AS ac
    ON ac.OwnerUserId = u.Id
LEFT JOIN UpvoteCounts AS uc
    ON uc.OwnerUserId = u.Id
LEFT JOIN CommentCounts AS cc
    ON cc.OwnerUserId = u.Id
WHERE u.Reputation >= 20000
ORDER BY
    ISNULL(uc.Upvotes2020, 0) DESC,
    ac.Answers2020 DESC,
    u.Id;
GO
