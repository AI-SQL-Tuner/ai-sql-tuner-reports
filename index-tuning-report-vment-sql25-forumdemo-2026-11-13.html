Detailed prioritized recommendations

1. Add an ordered covering index for the Posts owner-history query High confidence

Target statement: SELECT TOP (20) p.Id, p.Title, p.CreationDate, p.PostTypeId FROM dbo.Posts AS p WHERE p.OwnerUserId = @UserId ORDER BY p.CreationDate DESC, p.Id DESC.

The current IX_Posts_OwnerUserId has 16,120 seeks and no reported updates during the 2.4-day usage window, but it does not encode the requested ordering or cover the projected columns. The recommended key order is OwnerUserId, CreationDate DESC, Id DESC. Include Title and PostTypeId; Id is already available as the clustered key. This should reduce sorting and key lookups.

Estimated size: approximately 15–25 MB for 246,672 rows. Estimate is based on the supplied average widths of OwnerUserId 3.89 bytes, CreationDate 8 bytes, Title 24.06 bytes, PostTypeId 2 bytes, the 4-byte clustered key, plus row and page overhead. The exact estimate is uncertain because physical data types and nullability are not supplied.

The existing single-column index should initially remain. Its low-use-drop decision cannot be made safely because usage covers only 2.4 days; monthly or quarterly work may not have run.

2. Add a composite Votes aggregation index High confidence

Target statement: SELECT v.VoteTypeId, COUNT_BIG(*) AS Votes FROM dbo.Votes AS v WHERE v.PostId = @PostId GROUP BY v.VoteTypeId.

IX_Votes_VoteTypeId is led by the wrong predicate column for this query. The query executed 80 times in plan cache with average CPU 80,836 and average logical reads 1,539; Query Store reports 159 executions, average duration 81.78 ms, and average reads 1,535. Create (PostId, VoteTypeId) so the equality predicate and grouping are both supported.

Estimated size: approximately 17–22 MB for 945,284 rows. The supplied overlap candidate for PostId alone is 14.4 MB; the range adds the smallint-like VoteTypeId key, clustered-key locator, and page overhead. The table has 6,400 reported updates during the short usage window, so the additional write maintenance is acceptable only if the aggregation query remains part of the workload.

Do not add an unfiltered index led by the low-cardinality VoteTypeId; the reported distribution has only 13 estimated distinct values and would store rows that the query does not use as its leading filter.

3. Add an ordered Comments index and leave Text to lookups High confidence

Target statement: SELECT TOP (20) c.Id, c.Score, c.Text, c.CreationDate, c.UserId FROM dbo.Comments AS c WHERE c.PostId = @PostId ORDER BY c.CreationDate DESC, c.Id DESC.

The current IX_Comments_PostId has 32,000 seeks and 5.1 MB size, but it does not provide the requested order. Create (PostId, CreationDate DESC, Id DESC) and include Score, UserId. Do not include Text: its supplied average length is 180.97 bytes, and the query returns only up to 20 rows. Key lookups for that wide value are preferable to storing it in every index row.

Estimated size: approximately 10–18 MB for the reported 365,839-row index population, based on PostId 4 bytes, CreationDate 8 bytes, Id 4 bytes, Score 4 bytes, UserId approximately 3.71 bytes, the clustered locator, and overhead. The existing index has 4,800 reported inserts and should not be dropped solely on this short observation period.

4. Add an ordered Badges index Medium-high confidence

Target statement: SELECT b.Name, b.Class, b.Date FROM dbo.Badges AS b WHERE b.UserId = @UserId ORDER BY b.Date DESC, b.Id DESC.

The current IX_Badges_UserId has 12,000 seeks but does not provide the requested ordering. Create (UserId, Date DESC, Id DESC) and include Name, Class. The query executed 12,000 times in plan cache and Query Store reports 23,971 executions, average duration 0.29 ms, and average reads 171.

Estimated size: approximately 12–20 MB for 439,352 rows, based on UserId 4 bytes, Date 8 bytes, Id 4 bytes, Name 10.82 bytes, Class 2 bytes, clustered locator, and overhead. No Badges writes were reported in the usage or operational windows, reducing write-maintenance risk.

5. Re-trust the reported foreign keys after conditional validation High confidence

Nineteen foreign keys are enabled but not trusted, including relationships on Badges, Comments, PostHistory, PostLinks, Posts, Tags, Votes, and the AIIndexTuner tables. Untrusted constraints can block optimizer join elimination and predicate pruning. The supplied script checks for violating rows individually; each constraint is re-trusted only when no violation exists, otherwise a clear message is printed.

Validation scans can be expensive on large tables. No index storage change is associated with this recommendation.

6. Enable automatic statistics creation and updating High confidence

AUTO_CREATE_STATISTICS and AUTO_UPDATE_STATISTICS are both false. Enable them to allow SQL Server to maintain statistics needed by the recommended indexes and changing distributions. Because automatic update statistics is currently disabled, enabling asynchronous updates is also recommended to reduce synchronous statistics-refresh waits after auto update is enabled.

The supplied database is on SQL Server 2025 Enterprise Developer Edition, so online index operations and advanced compression are available. No statistics update or index rebuild is required immediately based on the reported page density.

7. Do not add columnstore or filtered low-cardinality indexes in this run High confidence

No large tables were reported. The largest supplied table, Votes at 945,284 rows, is below the 1,000,000-row threshold and has insert/update activity. The workload evidence is primarily selective OLTP lookups and ordered result sets, not a demonstrated analytic scan workload. A columnstore index would add write overhead: updates to compressed rows create delete markers and new delta-store versions, while trickle inserts accumulate in the delta store.

Skewed values exist for Posts.PostTypeId and PostLinks.LinkTypeId, but no supplied frequent query filters one of the rare literals in a way that justifies a filtered index. Do not create an unfiltered index led by those low-cardinality columns.
